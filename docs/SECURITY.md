# Безопасность локального CA

Show My Limits использует локальный mitmproxy CA для HTTPS-захвата выбранного сервера. Закрытый ключ хранится в каталоге данных пользователя и не отправляется приложением наружу. `--allow-hosts` ограничивает захват в работающем процессе, но **не ограничивает возможности украденного ключа CA**: mitmproxy может выпускать сертификаты для других имён. Чтобы перехватить чужое соединение, атакующему также нужен путь для подмены трафика.

## Доверие и хранение

- macOS: новые установки через GUI и CLI добавляют доверие в область текущего пользователя. Версии до этого изменения могли добавить CA в System/Admin; обновление приложения не удаляет старое доверие.
- Windows: автоматическая установка использует Current User Root. Linux: инструкции для Debian/Ubuntu добавляют CA в системный набор доверия; команда `sml trust` только печатает инструкции. Некоторые клиенты используют отдельное хранилище CA.
- Новые хранилища CA на macOS/Linux публикуются с правами каталога `0700` и файлов `0600`. Уже существующие файлы только проверяются; приложение не меняет их автоматически. Это не защищает от процессов того же пользователя и резервных копий.
- Для новых установок CA действует 365 дней и создаётся в отдельном закрытом каталоге. Генератор пишет только PEM-ключ с сертификатом, публичные PEM/CER и DH-параметры: дополнительный P12 с копией закрытого ключа не создаётся. Уже созданные CA не заменяются при обновлении.
- Перед использованием хранилища проверяются обычные файлы без символьных ссылок, совпадение встроенного сертификата с публичным CA и соответствие RSA-ключа открытому ключу сертификата. Созданные приложением CA используют RSA; другой формат ключа отклоняется. При несовпадении существующие файлы не заменяются.
- Повреждённое хранилище явно обозначается в GUI и `sml doctor`; отчёт для обмена содержит только категорию, без путей и ключа.
- В настройках «Захват» показаны SHA-256 действующего CA и обнаруженная область доверия. На macOS проверяются домены User/Admin, на Windows — Current User/Local Machine Root, на Debian/Ubuntu — точное совпадение сертификата с системным PEM bundle. Отдельные хранилища клиента и другие Linux-дистрибутивы эта проверка не охватывает. Предупреждение не удаляет доверие и не перевыпускает CA.
- Для обмена диагностикой используйте отчёт из настроек или `sml doctor --share`. Обычный `sml doctor` показывает локальные пути и отпечаток CA.
- Настройки показывают дату окончания CA и предупреждают за 30 дней. `sml doctor` печатает оставшиеся дни, а отчёт для обмена — только категорию срока без даты и отпечатка.

## Ограничение CA и перевыпуск

Name Constraints может ограничить имена в сертификатах, но [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280#section-6.1.1) допускает, что ограничения в самом trust anchor не применяются. [Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/policy/resources/templates/policy_definitions/Miscellaneous/EnforceLocalAnchorConstraintsEnabled.yaml) отдельно описывает своё поведение для локальных корней. Поэтому расширение нельзя считать защитой для всех клиентов без проверки macOS, Windows, Linux и Claude. [mitmproxy](https://docs.mitmproxy.org/stable/concepts/certificates/) допускает пользовательский CA, но совместимость генерации сертификатов и смены сервера также нужно проверить. В закреплённой версии 12.3.1 `CertStore.create_store` использует `create_ca`, где срок CA задан как `10 * 365` дней и нет Name Constraints ([исходный код](https://github.com/mitmproxy/mitmproxy/blob/v12.3.1/mitmproxy/certs.py)). Новый генератор сокращает срок до 365 дней; это не устраняет широкий охват уже доверенного корня и не гарантирует, что все клиенты проверяют срок самого trust anchor. Кнопку перевыпуска до проверки нового формата на целевых ОС не добавляем.

Старые CA будут перевыпускаться только по явному действию пользователя после проверки нового формата. Порядок: создать новый ключ и сертификат рядом со старым, подтвердить новое доверие, проверить захват, переключить приложение, затем отдельно предложить удалить доверие к старому CA по точному отпечатку. При ошибке пользователь должен иметь возможность вернуться к старому состоянию. Автоматической замены CA при обновлении нет.

См. [макет пользовательского пути](CA-ROTATION-FLOW.md) и текущие задачи в [WORKLIST.md](WORKLIST.md).
