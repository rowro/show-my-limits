# Прототип: CA без хранимого ключа

Цель: доверенный корень не должен позволять выпустить сертификат для произвольного сайта, даже если файлы приложения украдены.

## Схема

1. При настройке, когда сервер уже известен, приложение в памяти создаёт CA с Name Constraints `permitted DNS = <сервер>` и запретом любых IP.
2. Тем же ключом подписывается лист для сервера: SAN = сервер, serverAuth, срок 397 дней (меньше лимита Apple 825 дней и публичного 398).
3. Ключ CA не сериализуется и после выпуска недоступен. На диске остаются `ca.pem` (для доверия) и `leaf-chain.pem` (ключ листа, лист и CA, права 0600).
4. mitmproxy получает лист через `--certs <сервер>=leaf-chain.pem`. Собственный CA mitmproxy в `confdir` никому не доверен; `--allow-hosts` не даёт перехватывать другие хосты.

Что получает атакующий, укравший файлы: ключ листа, годный только для настроенного сервера. Выпустить сертификат для другого имени нельзя: ключа CA нет. Name Constraints — вторая линия обороны на случай, если ключ CA утёк в момент создания.

Цена: смена сервера в настройках и истечение листа требуют нового CA и нового подтверждения доверия, а затем удаления старого доверия по отпечатку. Ограничение `corp.example` по RFC 5280 разрешает и поддомены (`api.corp.example`); лист выпускается только для точного имени.

## Проверки

```sh
python -I tools/leaf-ca/run_checks.py <mitmdump> [--host corp-llm.test] [--json out.json]
```

Нужен Python с `cryptography` (ставится вместе с `mitmproxy==12.3.1`). По умолчанию хранилища доверия ОС не меняются: каждый клиент получает `ca.pem` явно. Chrome на Linux использует временную NSS-базу во временном `HOME`. Флаг `--os-trust` добавляет CA в машинное хранилище Windows, чтобы Chrome проверял сертификат системным верификатором; он работает только в GitHub Actions и удаляет CA после проверки. На macOS-раннере изменить доверие без диалога нельзя, поэтому Chrome на macOS проверяется вручную. Воркфлоу: `.github/workflows/ca-constraints.yml`.

Для каждого верификатора проверяется: лист для сервера и поддомена принимается; `evil.test`, `<сервер>.evil.test` и `not<сервер>` отклоняются. Через mitmproxy проверяется: клиент получает наш лист и заголовки квот; хост вне `--certs` подписывается недоверенным CA mitmproxy и отклоняется.

## Результаты 2026-11-24

| Окружение | Верификаторы | Итог |
|---|---|---|
| macOS 27 arm64 (локально) | OpenSSL 4.0.3, Python ssl, Node 22, Security.framework, curl/LibreSSL 3.3.6 | 30/30; curl/LibreSSL принимает `not<сервер>` (WARN, см. ниже) |
| Debian 13 arm64 (Docker) | OpenSSL 3.5, Python ssl, Node, curl/OpenSSL, Chromium 156 через NSS | 30/30 |
| Windows Server, GitHub Actions | OpenSSL, Python ssl, Node, curl/Schannel, CryptoAPI (X509Chain), Chrome через Local Machine Root | все проверки прошли |
| Ubuntu 24.04 x64 и arm64, GitHub Actions | OpenSSL, Python ssl, Node, curl/OpenSSL, Chrome через NSS | все проверки прошли |
| mitmproxy 12.3.1 `--certs` | обычный режим прокси | лист отдаётся, квоты доходят, чужой хост отклоняется |

LibreSSL сравнивает ограничение имени как строковый суффикс, поэтому `notcorp.example` проходит ограничение `corp.example`. Это слабость конкретного клиента (системный curl macOS), а не схемы: для эксплуатации всё равно нужен ключ CA. Claude Desktop (Chromium) и Claude Code этой библиотекой не пользуются.

## Ручная проверка на macOS, 2026-11-24

macOS 27 arm64, `/opt/homebrew/bin/mitmdump` 12.3.1 в режиме `local:Claude,claude` с `--certs`, аддон проекта, корпоративный хост из настроек. Тестовый CA добавлен в связку входа с доверием только для SSL; после проверки доверие и сертификат удалены.

- Режим `local` с `--certs` работает: клиент получил лист тестового CA, аддон записал квоты (`quota_received`).
- Чат Claude Desktop и процессы Claude Code, запущенные **после** добавления доверия (новая сессия вкладки Code, терминальный `claude` 2.1.331), прошли TLS.
- Процессы Claude Code, запущенные **до** добавления доверия, отклоняют сертификат: Claude Code читает системные корни один раз при запуске, а Chromium перечитывает их сам. Отклонение было ровно одно на каждый такой процесс.

Вывод для приложения: после установки доверия нужно просить перезапустить Claude Desktop и открытые сессии Claude Code; без этого первая проверка «свежих квот» упадёт с ошибкой сертификата у старых процессов. Это касается и перевыпуска CA.

Отдельно: старый mitmproxy CA этой машины доверен в домене Admin (тоже только для SSL); его уборка — часть явного перевыпуска.

## Что ещё не проверено

- Chrome/Electron на macOS через системное доверие в CI: на раннере его не изменить без диалога. Вручную проверено через Claude Desktop.
- Windows и Linux с реальными клиентами Claude и режимом `local`.
- Перенос в приложение (`src-tauri/src/certificate.rs`, rcgen) на macOS проверен нативно 2026-11-24; Windows и Linux — нет.
